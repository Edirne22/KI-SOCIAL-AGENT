## 2. Risikoanalyse für den Produktivpfad

bei der Übernahme von V8.6 nach `main` bestehen folgende Hauptrisiken:

1. **Breaking Change bei Telegram Router & Atomic Processing**:
   - *Risiko*: `telegram_receive.py` und `telegram_router.py` wurden stark umgebaut. Wenn Updates falsch verarbeitet werden oder Exit-Code 2 Unerwartetes auslöst, könnten Telegram-Befehle oder Freigaben verloren gehen.
   - *Gegenmaßnahme*: Lokale Ausführung der Telegram Deduplizierungstests und Re-Entranz-Tests vor Live-Schaltung.

2. **Abhängigkeit von neuen Hilfsmodulen (`hashtag_database.py`, `racing_cfo.py`)**:
   - *Risiko*: Fehlen Importe oder Konfigurationsdateien auf `main`, bricht `motogp_content_agency_v2.py` beim Start ab.
   - *Gegenmaßnahme*: Vollständiges Promoten aller neuen Module vor der Aktivierung des Workflows.

3. **Verlust historischer Logik durch gelöschte Skripte (`archive_published.py`, `scripts/*`)**:
   - *Risiko*: Falls externe Cronjobs oder Workflows noch auf `archive_published.py` zugreifen, schlagen diese fehl.
   - *Gegenmaßnahme*: Prüfung aller `.github/workflows/*.yml` auf Aufrufe gelöschter Skripte.

---

## 3. Rollback-Strategie

Sollte es nach der Promotion auf `main` zu unvorhergesehenen Fehlern kommen, greift folgender Stufenplan:

1. **Sofort-Aktion (Automatischer Stop)**:
   - Deaktivierung der GitHub Workflows (`motogp-content-agency.yml`, `telegram-receive.yml`) via Workflow-Dispatch Pause oder Git Revert des Workflow-Commits.
2. **Git Backup-Point**:
   - Vor dem Merge wird auf `main` ein Tag gesetzt: `git tag backup-pre-v8.6-promotion`.
3. **Rollback Durchführen**:
   - Im Ernstfall: `git revert -m 1 <promotion-commit-sha>` oder Revert des PRs auf GitHub.
   - Wiederherstellung des stabilen V8.5 Zustands.

## 6. Auflösung des Debug-Workflow-Splits

### Ist-Zustand
Derzeit läuft der diagnostische Test-Workflow auf der Branch `debug/motogp-pipeline-output`, während die Workflow-Definition auf `main` gepflegt wird. Dies führt zu Konfigurations-Drift und unübersichtlichen Testergebnissen.

### Soll-Zustand & Auflösungsvorschlag
1. **Nach erfolgreicher Promotion von V8.6 auf `main`**:
   - `.github/workflows/motogp-pipeline-diagnostic.yml` wird so konfiguriert, dass er standardmäßig auf `main` läuft (`branches: [main]`).
2. **Stilllegung des Debug-Branches**:
   - Nach Verifizierung aller Testläufe auf `main` wird `origin/debug/motogp-pipeline-output` eingefroren / archiviert und kann gelöscht werden, da `main` den voll funktionsfähigen Stand V8.6 abbildet.
3. **Einheitliche Single Source of Truth**:
   - Alle Pipelines, Diagnosen und Publisher laufen wieder ausschließlich auf `main`.
